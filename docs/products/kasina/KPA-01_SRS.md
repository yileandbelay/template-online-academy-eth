v1.2 applies the owner decisions in `DECISIONS.md` (D-01 to D-06). Each changed sentence is tagged `[v1.2: D-xx]`. Phase 2 requirements were added as section R-P2. All other text is unchanged from v1.1.

# Scope and authority
Phase 1 is a bilingual web application and installable PWA for a single academy, approximately 30 hours of initial content and 10–500 paying students annually. Phase 2 is Telegram distribution and online payments, with earlier gateway activation only by explicit approval after readiness checks. Schedule: 8 weeks in total; Phase 1 in weeks 1–4, Phase 2 in weeks 5–8 (see BUILD_PLAN.md) [v1.2: D-05]. The system is built from scratch by Hulu Software Labs; no existing codebase is reused [v1.2: D-01]. No marketplace, physical class administration, retail, native app or offline protected video. KPA-04 v1.1 is the master product specification; this SRS formalizes its functionality and rules. KPA-03 is excluded from this package by owner instruction. Screen IDs below map directly to KPA-04; requirement IDs use the prefix R-. The original architecture is historical input, not an overriding specification.
# Common business rules
R-CORE-01 | One identity, three portals. Student self-registration only. Instructor has assigned academic scope; admin has all management scope. Staff student access requires enrollment like any other student. Enforce permissions server-side, including direct URLs and object IDs.
R-CORE-02 | Three curriculum types: Lesson, Quiz, Practical assessment. Required activities equally weighted; optional excluded. Video completion requires 90% unique playback coverage; non-video lesson explicit completion; assessments require pass. No progression locks. For a course with zero required activities, do not auto-complete; require at least one required activity before catalog publication .
R-CORE-03 | New required activities affect incomplete enrollments only; completed records and certificates remain valid. Reorder and text edits preserve progress. Video replacement preserves earned completion but resets incomplete playback coverage. Quiz edits preserve valid passes and historical attempts. Archive records; archived required activities leave current requirements but retain history. Warn before changing requirements.
R-CORE-04 | Separate payment, access and academic states. Payment: awaiting payment, pending verification, confirmed, rejected, cancelled. Access: active, expired, suspended. Academic: not started, in progress, completed. One persistent student/course enrollment. Renewal extends from max(expiry, confirmation time); default duration 90 days, configurable per course. Preserve progress. Free and complimentary access create no fictional revenue.
R-CORE-05 | Money in integer ETB minor units. Verified receipt date in Africa/Addis_Ababa local calendar; Gregorian display baseline. Revenue insight = confirmed valid payments by verified receipt date; no gross/net framework or accounting ledger. First activation counts new enrollment; renewal separately. Admin cash self-confirmation permitted with audit and owner reconciliation. Refunds only under approved legal policy; no silent confirmed-record edits.
R-CORE-06 | Cohort selected by first activation date; completion measured as of report generation. Unique students distinct identities. Access independent of completion. CSV matches filters and grouping. Financial reports and Academic & enrollments only.
R-CORE-07 | No staff MFA in Phase 1: all users sign in with phone and SMS OTP [v1.2: D-04]. Session revocation; audit actor/time/old/new/reason. Sensitive bank-account changes require a fresh SMS OTP (step-up), are audited and trigger an SMS and in-app alert to the administrator's verified phone; one administrator is sufficient and no second-owner notification is required [v1.2: D-03, D-04]. Private submissions, approved retention. No public certificate verification or automatic national qualification. One certificate per student/course; print date generated on download. Exceptional invalidation only verified error/fraud with audit; legal policy pending.
R-CORE-08 | All lists loading/empty/filtered empty/error-retry; forms validation/saving/success/failure/unsaved warning. Upload progress/processing/retry; playback interruption recovery. Accessible keyboard focus, labels, contrast, touch targets and screen reader checks. Preserve safe return route on session expiry. Amharic default, English optional, persistent language switch; teaching language independent.

# Phase 2 requirements (weeks 5–8) [v1.2: D-05]
Phase 2 extends TG-001 and STU-003. It uses the same Student Portal, records, rules and screen IDs as Phase 1. No separate Telegram application and no new management screens. The detail below comes from the Architecture and Implementation Spec (23 November 2026) and KPA-02. Items marked *validate* are gates to confirm in week 5 before building on them.

## R-P2-01 | Telegram Mini App container
The complete Student Portal (STU-001–011) runs inside a Telegram Mini App opened from the Learn at Kasina bot. It uses the same build and routes, in a Telegram-aware shell:
- theme and viewport handling, BackButton mapped to in-app back, safe areas
- no public marketing pages or management portals
- an admin or instructor opening the Mini App sees the Student Portal only

External links (public website, payment checkout if required by R-P2-06) open through Telegram's link-opening API.

## R-P2-02 | Telegram authentication
The server verifies Telegram init data on every Mini App session start:
- the HMAC signature computed from the bot token
- auth_date freshness (proposed maximum age 24 hours; *validate*)

Never trust init data unsigned or from the client. A verified Telegram user with a linked account gets a normal server session (same session model, revocable).

## R-P2-03 | Identity linking
On first verified Mini App launch with no linked account, the student confirms their phone number with the same SMS OTP flow (AUTH-001). If the phone exists, telegram_user_id is linked to that existing user; never create a duplicate identity. If not, a new student is registered. One Telegram user ↔ one Kasina user; relinking requires an OTP on the new phone, is audited and revokes Telegram sessions.

STU-011 shows the account-linking section (hidden in Phase 1) with linked status and an unlink action.

## R-P2-04 | Bot notifications
The bot sends personal notifications through the existing notification outbox as an added channel (ADM-019):
- payment confirmed or rejected
- assessment result
- course announcement
- access expiring and expired
- certificate available
- message reply

Sending requires that the user started the bot (consent) and has a linked account. Each message deep-links into the relevant record via the Mini App start parameter. Delivery failures are retried and recorded, and never undo the underlying event. The public Telegram channel stays marketing only and is not automated.

## R-P2-05 | Deep links
Deep links to a course detail page, payment status, a lesson, a certificate and a conversation. The Mini App start parameter carries an opaque route token, never raw IDs with authority. Authorization is re-checked on open.

## R-P2-06 | Online payment (Chapa)
- STU-003 adds the "Online payment" method when it is enabled in ADM-017 ("Online: Not configured" until set up). Bank and cash remain available.
- **Initialize:** the server creates the order as in Phase 1 (quoted price, duration snapshot and purpose initial/renewal) and initializes a Chapa transaction with a unique tx_ref. The student completes payment on Chapa's hosted checkout.
- **Confirm:**
  - On callback or webhook, the server verifies the transaction with Chapa's verify API. Never trust the redirect or the webhook body alone; also verify the webhook signature if Chapa provides one (*validate*).
  - It checks status, amount, currency and tx_ref against the order.
  - It then confirms through the same atomic, idempotent confirmation transaction as R-ADM-006, with actor "system (Chapa)". The confirmed payment is unique per provider transaction ID.
  - Repeated webhooks return the existing result.
- **Statuses:** awaiting payment → confirmed, or failed/cancelled. Abandoned checkouts expire under the approved stale-order rule.
- **Reports:** the payment method "Online (Chapa)" appears in ADM-006 and ADM-008. The amount recorded is the amount paid; no fee netting or gross/net (R-CORE-05).
- **Reconciliation:** daily against the Chapa dashboard.
- **Fallback:** SantimPay sits behind the same payment-provider interface; implement only if Chapa is unavailable.
- **Fees (reference):** Chapa about 2.5% domestic and 1% international; *validate* current rates.
