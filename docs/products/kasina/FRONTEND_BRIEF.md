## First deliverable
[v1.2: D-05, D-06] The frontend is built in weekly vertical slices alongside the API, not as a complete mock application first. Each week: define contracts in packages/contracts, implement the API and domain rules, and build the screens against the real API on staging. Use mock adapters only for endpoints not yet implemented, behind the same contracts, returning deterministic fixtures; never reimplement business rules (grading, coverage, completion, renewal, report totals) in mocks; delete each mock when its endpoint lands. The original requirement still applies to mocks while they exist: build a navigable React/TypeScript responsive PWA frontend with deterministic mock data and typed repository/service interfaces. No real payments, OTP, provider uploads or production secrets. Start a new repository from scratch [v1.2: D-01]: scaffold the KPA-02 monorepo with React, Vite and TypeScript, routing and shared components; if Hulu has already initialized it, preserve its conventions. Use mock adapters behind the same contracts intended for API integration. Clearly mark demo actions. Persist mock state locally only for non-sensitive fixtures; never imply real transactions. Provide reset demo data and role switch for testing, not production authorization.

## Routes and build order
The order below is the dependency order. Weekly timing is in BUILD_PLAN.md (week 1: 1–2; week 2: course parts of 4, student learning and payment parts of 3, payments in 6; week 3: assessment parts of 3 and 4, 5; week 4: rest of 6 and 3; TG-001 preparation in week 4) [v1.2: D-05]. Proposed routes are in docs/TRACEABILITY.md.
1. Public shell, homepage, catalog/Explore, course details/free preview, About/contact (PUB-001–006). Same catalog components for signed-in Explore; no personalized badges.
2. Auth (AUTH-001–002): phone, registration, OTP (same for staff; no MFA [v1.2: D-04]), step-up OTP for bank-account changes, authorized portal switching; preserve enrollment intent.
3. Student (STU-001–011): My Learning, Explore, Certificates, Account; payment method and status, player, consolidated assessments, quiz, practical upload/review, certificate preview, account history/notifications/support. Mobile four tabs. No top-level materials or assessments.
4. Shared academic (ACD-001–011): Details, Curriculum, Assessments, Students, Announcements; one editor reused by admin/instructor. Three activities only. Optional modules; lesson optional video/text/files; provider states; quiz editor/results; practical editor/review; academic record. Admin-only commercial controls. Preserve mock progress on reorder and renewal.
5. Instructor (INS-001–004): Dashboard, My courses, My students, Assessments, My profile. Assigned courses only; mobile Dashboard/Courses/Assessments/Profile. Shared review queue and academic editor.
6. Admin (ADM-001–020): Dashboard, Manage courses, Manage staff, Manage students, Payments, Certificates, Reports, Messages, Settings, in that order. Mobile Dashboard/Courses/Payments/Website plus full menu. Reports exactly two tabs, working filters/grouping/totals/chart/CSV. Messages shared inbox and conversation, open/resolved independent of read. Six settings sections with structured fields, not website builder.
7. TG-001: prepare reusable student shell and adapter boundary only; no Phase 2 integration now.

## Mock scenarios and behavior
Use one consistent fixture store: two certificate courses, two short courses including free, assigned instructors and admins, multiple student enrollments with active/expired/completed states, pending/rejected/confirmed payments, renewal and complimentary grant, quiz attempts and practical pending/passed/resubmit. Keep totals derived from fixtures, not hard-coded inconsistent numbers. Implement mock payment confirmation and rejection/resubmit, access activation/renewal, 90% unique video coverage simulation, quiz grading, practical review, completion/certificate, notifications, course announcement, messages and settings updates. Separate payment/access/academic state. Simulate errors and loading, preserve unsaved changes, no real SMS/email. No fake success for unavailable integrations.

## Review before backend
Run typecheck, lint, build and automated interaction tests. Demonstrate every screen ID and critical state; capture desktop/mobile screenshots, check Amharic wrapping and keyboard navigation. Provide README with run commands, demo identities, routes, component map, mock data assumptions, known limitations and unresolved decisions. Deliver small commits and stop for owner review at the end of each week on staging (BUILD_PLAN.md) [v1.2: D-05]. Do not silently change scope or claim production readiness. Telegram and gateway integration are Phase 2 unless earlier gateway activation is explicitly approved. Actual service limits, legal text, assets, translations and security are release gates.

## Final review controls
Maintain a screen ID, route, component and status matrix. Use authorized academy assets. Preserve agreed layouts. Demonstrate each portal's screens at the weekly review in which they are built [v1.2: D-05]. Revenue reports show confirmed valid payments only; no gross/net accounting. Require at least one required activity before catalog publication. Archived required activities leave current requirements but retain history. Preserve earned completion on video replacement; reset incomplete playback coverage. Renewal uses purchased duration. Prevent duplicate open purchase requests; honor valid quoted price. Course type changes after enrollment require controlled migration. Disable staff with session revocation; prevent disabling last active administrator. Message read state per administrator; resolution shared. Timely practical submissions may be reviewed after expiry and earn completion/certificate; new attempts require active access.
