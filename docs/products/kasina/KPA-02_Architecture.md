# Architecture & Implementation Specification

Version 1.2 | 26 November 2026 | Hulu Software Labs PLC for Kasina Pastry Academy

v1.2 applies the owner decisions in `DECISIONS.md` (D-01 to D-06). Each changed sentence is tagged `[v1.2: D-xx]`. Phase 2 technical detail was added in the section "Phase 2 integration (weeks 5–8)". All other text is unchanged from v1.1.

# Architecture decision and scope
Source: original Kasina Academy Architecture and Implementation Spec, 23 November 2026, and KPA-04 v1.1, 25 November 2026. KPA-04 is the master product specification; KPA-01 formalizes its requirements. Selected stack: React + TypeScript + Vite PWA frontend and TypeScript Fastify API, so that frontend components and typed contracts are shared across the public site, the three portals and the Telegram Mini App [v1.2: D-02]. Hulu Software Labs builds the system from scratch in a new repository; there is no existing code [v1.2: D-01]. Phase 1 bank/cash; Phase 2 Chapa (SantimPay alternative) and Telegram. Earlier gateway release requires approval. No KPA-03 dependency.
# System boundaries | R-CORE-01, R-CORE-08
React TypeScript PWA served over HTTPS; Fastify API, PostgreSQL 16 with migrations and PostgreSQL-backed job queue. One deployable modular backend, not microservices. Modules: identity, catalog/content, learning/assessments, payments/access, certificates, messaging/notifications, reporting/settings/audit. Browser calls API; API authorizes each object and returns short-lived media URLs. Bunny Stream and private storage deliver media directly. SMS/email and later Telegram/Chapa adapters are server-side. Same student UI in Telegram; no management routes exposed in Mini App.
Use one repository with apps/web, apps/api, packages/contracts, packages/ui, packages/i18n, migrations and tests. Shared typed request/response schemas, runtime validation at API boundary, generated or shared types. Use /api/v1; opaque IDs, UTC timestamps, Addis Ababa reporting dates, paginated lists, stable sorting and consistent error codes. Do not expose database models directly. Keep secrets outside repository. Service worker caches static shell/public assets only, not private media, receipts or authenticated API responses.
# Data model and invariants | R-CORE-01–07
users: id, normalized unique phone, verified_at, name, email optional, locale, student_code, disabled_at. roles/user_roles and course_instructors: scoped membership, explicit grants; staff_profiles: bilingual public fields and visibility. sessions, otp_challenges: hashed tokens/codes, expiry, revocation; step_up_challenges (or an OTP purpose field) for sensitive actions. No MFA tables in Phase 1; keep authentication in one module so MFA can be added later without changing callers [v1.2: D-04]. Phase 2 adds users.telegram_user_id (nullable, unique) and telegram_links audit [v1.2: D-05].
courses: type CERTIFICATE/SHORT, bilingual metadata, teaching language, price_minor, access_days, publication state, cover, version. course_groups and course_group_memberships: reusable many-to-many. modules optional; activities: course_id, module_id nullable, type LESSON/QUIZ/PRACTICAL, position, required, publication state, archived_at, version. lesson_content: rich text, optional video_id; attachments: private object metadata and authorized preview flag. videos: provider, provider_id, duration, processing state. quiz_versions, questions, choices: immutable published assessment snapshots; practical_versions: instructions, criteria and supporting material.
orders: student/course, purpose initial/renewal, amount_minor, currency, duration snapshot, status, receiving account snapshot, reference, timestamps. payment_attempts: receipt object, normalized transaction reference, received date, decision actor/reason. confirmed_payments: unique order_id and provider/account-scoped transaction reference, immutable amount/date. payment_corrections: original payment, amount, type, effective date, reason, actor. Bank account records deactivate rather than delete. Prevent duplicate confirmed references across accounts where provider identifiers are globally unique; verify provider semantics before launch.
enrollments: unique(student_id,course_id), first_activated_at, expiry_at, suspension, completed_at; access_events: source order or complimentary grant, previous/new expiry, actor/reason. activity_progress: unique enrollment/activity, resume position, merged watched intervals, completed_at. quiz_attempts: version, answers, score, submitted_at; practical_attempts: private object, notes, version, state, submitted_at, reviewer, feedback, reviewed_at. Preserve historical passes. certificates: unique enrollment_id, completion snapshot, identity correction history, invalidation state; no public verification endpoint.
announcements, conversations, messages, conversation_reads, notifications, notification_outbox, academy_settings, localized_site_content, audit_log. Conversation owner nullable for public inquiry; external contact details protected. Read status per administrator recommended; shared open/resolved status. Audit append-only through application, restricted DB access. Store file keys, not public URLs. Retention jobs must follow approved policy; preserve necessary academic and financial metadata.
# Transactions and state transitions | R-CORE-02–07
Payment confirmation: lock order and enrollment key; validate state, amount and reference; insert unique confirmed payment, upsert enrollment/access event, update order and audit/outbox in one transaction. Retry returns existing result; notification delivery outside transaction. Rejection requires reason; resubmission adds attempt, does not overwrite. Cash authorized admin can record/confirm atomically. Reconcile daily against bank/cash records. Corrections use separate adjustment; access effect explicitly authorized and audited, never silently revoke earned certificate. Refund policy is launch gate.
Renewal: expiry = max(existing expiry, confirmation instant) + purchased access duration; use agreed local-day semantics consistently (proposed elapsed 24-hour days). First activation immutable. Complimentary grant audited without payment. Lock concurrent orders and prevent duplicate initial activation; renewal orders explicit. Pending orders retain quoted price/account/duration; stale orders require explicit cancellation/requote, expiry policy to approve.
Learning: API verifies active access and published activity or authorized preview. Track unique playback coverage by merging bounded intervals from player events; reject impossible jumps, not a guarantee of attention. Non-video explicit mark complete. Quiz grade on server against immutable version; equal weights, all correct choices for multi-select; preserve best valid pass. Practical review uses conditional update on pending attempt/version; reject stale concurrent review. Timely submissions reviewable after expiry, new attempts require active access. Completion transaction checks all current required activities, sets completion once and inserts unique certificate for certificate course. New required content changes incomplete cohorts only; completed_at immutable except audited exceptional correction. Zero required activities guard per SRS.
# API surface and authorization
Proposed route families (final schema in code): /auth/otp/request, /auth/otp/verify, /auth/step-up, /sessions [v1.2: /auth/mfa removed, D-04]; Phase 2: /auth/telegram, /me/telegram-link, /me/orders/{id}/online-checkout, /webhooks/chapa [v1.2: D-05]; /catalog/courses, /catalog/groups, /site; /me/enrollments, /me/orders, /me/certificates, /me/notifications, /me/conversations; /courses/{id}/activities, /activities/{id}/playback, /progress, /quiz-attempts, /practical-attempts; /manage/courses, /manage/staff, /manage/students, /manage/orders, /manage/reviews, /manage/reports, /manage/messages, /manage/settings, /manage/audit. Separate public projections from private records. Every mutation validates role, course scope, state and ownership; never trust client role or price. Use idempotency keys for payment and submission creation, optimistic version for editors/reviews, CSRF protection for cookie sessions, rate limits and structured error responses. Public contact endpoint rate-limited and spam-protected. Signed upload initiation and finalize endpoints verify object ownership, size/type and processing status.
# Media, authentication and security
Original architecture: 6-digit SMS OTP, 5 minutes, 5 tries, rate-limited. Normalize +251 numbers; generic responses to avoid account enumeration. Secure HttpOnly SameSite cookies, rotate on login/privilege change, revoke on logout/disable/recovery. Staff use the same phone + SMS OTP sign-in as students; no MFA in Phase 1 [v1.2: D-04]. No self-elevation. Bank-account changes require a fresh step-up OTP for that action, are audited and send an SMS and in-app alert to the administrator's verified phone; one administrator is sufficient [v1.2: D-03]. Staff sessions may use shorter idle and absolute lifetimes than student sessions; session durations require approval (implement as configuration). Use least privilege, dependency scanning, CSP, sanitized rich text, upload MIME/signature validation and malware scanning where feasible. No secrets or full receipts in logs.
Bunny Stream private library, signed short-lived player links, allowed domains, MediaCage where supported and visible student-code watermark. Direct browser upload using narrowly scoped credentials; no permanent API key. Verify processing via authenticated callback or polling. YouTube public/unlisted links are not protected; warn for paid content; validate playback completion integration. Server-hosted short videos authenticated, range requests, tested size limits; no adaptive promise. Private practical videos and receipts separate from teaching library; signed access only authorized student/admin/assigned reviewer as appropriate. No public reuse. Screen recording cannot be fully prevented. Test upload retries, interruption and low quality streaming on Ethiopian networks.
# Reporting, jobs and operations
Revenue query uses valid confirmed payments by verified receipt date, excluding invalidated payments; corrections remain audited operational records, not accounting reports; group/filter by course/type/month/method/account/purpose. Academic cohort by first activation; as-of generation completion and access counts; unique students distinct IDs. CSV uses same query, UTF-8 and safe escaping against spreadsheet formula injection. Index enrollment/course/date, payment received date/status, review pending, notification recipient, conversation state and audit time. No separate analytics engine.
Outbox worker handles SMS, email, in-app notices, expiry reminders and later bot delivery; deduplicate by event/recipient/channel, retry with backoff, record failures, avoid duplicate notices on announcement edits. Essential in-app notices always enabled; SMS optional per settings; OTP independent. PDF certificates generated server-side using Noto Sans Ethiopic, five fields, no QR. Settings are validated typed records, not arbitrary code; provider disabling affects new uploads only. Legal terms version captured at purchase/registration where applicable (proposed implementation detail).

Weekly staging demos, small reviewable changes. Handover repository, service accounts, deployment/runbook, admin guide and staff training.

# Final synchronized safeguards
Require at least one required activity before catalog publication. Archived required activities leave current requirements but retain history. Preserve earned completion on video replacement; reset incomplete playback coverage. Renewal uses purchased duration. Prevent duplicate open purchase requests; honor valid quoted price. Course type changes after enrollment require controlled migration. Disable staff with session revocation; prevent disabling last active administrator. Message read state per administrator; resolution shared. Timely practical submissions may be reviewed after expiry and earn completion/certificate; new attempts require active access.
Serialize curriculum changes and completion evaluation. Authorize public preview assets separately. Back up private receipts, submissions and media metadata. Validate playback tracking per provider before production. Corrections cannot exceed original payment; no accounting subsystem.

# Engineering contracts and release controls
Database: foreign keys from activities to courses/modules, enrollments to users/courses, orders to users/courses, attempts to enrollment/activity/version, certificates to enrollment. Enforce module/course consistency with composite keys; restrict destructive deletes. Unique enrollment(student,course), confirmed payment(order), access event(source order), certificate(enrollment), progress(enrollment,activity), course instructor(course,user). Partial unique open order(student,course,purpose) for awaiting/pending/rejected; close stale requests explicitly. Check nonnegative integer amounts, positive duration, valid enum states and review decision/feedback consistency. Lock payment order then enrollment, and serialize course curriculum changes and completion evaluation using course row lock; use consistent lock order. Retry serialization failures safely.
API contract baseline: JSON with opaque IDs and ISO UTC dates, integer minor units, typed enum states. Success 200/201; validation 400, unauthenticated 401, forbidden 403 or scoped 404, stale version/duplicate conflict 409, rate limit 429, unavailable 503. Error envelope {code,message,fieldErrors,requestId}; never return secrets. POST /manage/orders/{id}/confirm accepts verified received date, reference, expected version and idempotency key; returns order, payment and enrollment IDs plus expiry. POST /manage/reviews/{id} accepts version, decision, feedback; returns updated attempt. Both authorize at commit. Define complete OpenAPI schemas and permission tests in repository before connecting frontend.
Private uploads: authorize initiation and finalize, verify declared and actual size/type, quarantine until signature and malware checks succeed, deny public access, short-lived signed reads, delete rejected objects per approved retention. Provider spike must demonstrate unique playback coverage and signed media; do not enable unverified provider for required video lessons.
Staff recovery [v1.2: D-03, D-04]: a staff member who loses their phone is re-pointed by the administrator to a new verified number (identity checked offline, step-up OTP by the admin, audited, all sessions revoked). If the only administrator loses their phone, Hulu runs an audited server-side operator command (for example `pnpm --filter api ops:admin-phone-reset`) that sets the new number, revokes sessions and writes an audit entry with the operator's name and reason; documented in the runbook. Prevent last-admin disable. Approve session durations before launch.
Operations: daily encrypted database and private-object backups with manifest and checksums; restore to isolated staging monthly, reconcile object keys and test playback/receipts, measure RPO/RTO. Migrations tested on restored snapshot; backward-compatible deployment, health check and rollback to previous image; destructive migration requires tested restore plan. Alert on backup failure, disk capacity, queue lag and payment errors; assign owner and escalation contact before launch.

# Phase 2 integration (weeks 5–8) [v1.2: D-05]
Telegram (R-P2-01 to R-P2-05, R-P2-08):
- **Bot and Mini App:** registered under Kasina's Telegram account; the bot token is server-side only.
- **Mini App authentication:**
  - The frontend sends the raw initData string to /auth/telegram.
  - The server validates the HMAC with the bot-token-derived key and checks auth_date freshness.
  - It then issues the normal session cookie. If the cookie is unavailable in the Telegram webview on any platform, fall back to a short-lived bearer token held in memory; *validate* in week 5.
- **Linking:** an unlinked Telegram user completes SMS OTP. Link to the existing user by phone, or register a student. Unique telegram_user_id; audited relink.
- **Bot delivery:** a telegram channel in notification_outbox, deduplicated per event/recipient/channel, retried with backoff. Respect bot blocked/stopped (mark the channel inactive).
- **Shell:** the frontend detects Telegram (window.Telegram.WebApp) and switches to the student-only Telegram shell. Management routes are not registered in that shell and the server still rejects them by scope.

Online payment (R-P2-06, R-P2-07):
- **PaymentProvider interface:** `initialize(order) -> checkoutUrl`, `verify(providerRef) -> {status, amount, currency, providerTxnId}`, `parseWebhook(req)`. ChapaProvider is implemented; SantimPayProvider only as a fallback.
- **payment_events:** stores each webhook/callback raw (redacted), signature result, provider transaction ID and processing result, unique on (provider, provider_event_id or txn ref + status).
- **Confirmation:** calls the same confirmPayment transaction used by ADM-006, with actor system:chapa, idempotent on the provider transaction ID. Amount/currency mismatch → hold for admin review, never auto-confirm.
- **Secrets:** Chapa secret key and webhook secret held in deployment configuration only.
- **Test mode:** Chapa test keys on staging; production keys only after the R-P2-07 gate.
